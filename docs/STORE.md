## 1. 問いと経緯

プロジェクトの本筋は次のとおりである（SPEC §1.2）。

```text
USB 接続 → 文字起こし → LLM 要約 → Obsidian へ 2 枚のノート → 元音声を削除
```

この筋に対して、**SQLite を選んだことの副作用が §8.5 のドクトリンとして固定されていた。**

| 旧ドクトリン（§8.5） | なぜそう決めたか |
|---|---|
| テーブルを作り直してはならない | `AUTOINCREMENT` が振り直されると**削除事故になる**（下記） |
| スキーマは v1 完全形とする | 同上。作り直さずに済むよう、最初から全列を持つ |
| v2 以降は `ALTER TABLE ADD COLUMN` に限る | 同上 |
| ファイルコピーでバックアップしてはならない | WAL のため。`Connection.backup()` を使う |

**「削除事故」の中身**: §14.1 の削除条件は `part.id in frontmatter_ids(note)` であり、
**削除可否を `recordings.id` の同一性に賭けている。**ノートの frontmatter には
`voicedock_recording_ids: [41, 42, 43]` と整数が載る。SQLite 定番の
「新テーブル作成 → `INSERT SELECT` → `RENAME`」でスキーマを変えると `AUTOINCREMENT` が
振り直され、**ノートに載っている 42 と DB の 42 が別の Part を指しうる。**
そのとき §14.1 は真になり、**文字起こしが Vault に無い音声を削除する。**
これは §20.4 の ND-01〜ND-30 がどれも検出できない経路である。

これだけの制約を背負う根拠があるのかを確かめるのが #60 である。

## 2. 規模

| 指標 | 値 | 出所 |
|---|---|---|
| `recordings` の行数 | **年 1.2 万行**（1 日 32 Part） | §5.1 の終日録音の前提 |
| `sessions` の行数 | **年 365 行**（1 デバイス・1 日で 1 行） | §8.3 |
| `events` の行数 | **年 8.2 万行**（1 Part あたり約 7 遷移） | §8.4 |
| 書き込みプロセス数 | **1**（`service` のみ） | §10.0 のワーカーループ。`docker compose exec` は読み取り |
| 結合を要する照会 | **なし** | `status` / `doctor` が状態別に数えるだけ（§17.2 / §19.2） |
| トランザクションの範囲 | **1 エンティティ**（`status` UPDATE + `events` INSERT） | §8.4 `record_transition()` |

**RDBMS を必要とする形の負荷ではない。**行数は少なく、書き手は 1 つで、結合が無い。
だから「SQLite は本当に必要か」という問いは正当である。

## 3. 実測

### 3.1 測定方法

```bash
docker build --target dev -t voicedock:dev .
docker run --rm -v "$PWD/poc:/poc:ro" voicedock:dev python /poc/store_bench.py /tmp/store_bench
```

`poc/store_bench.py` は 3 年分（`recordings` 35,040 / `sessions` 1,095 / `events` 245,280）を
生成し、**SPEC が実際に行う 4 つの操作だけ**を計測する。

| # | 操作 | どこで使うか |
|---|---|---|
| 1 | 状態別の件数集計 | §17.2 `status` の Parts / Sessions のバケット |
| 2 | `partkey` の重複判定 | §10.2 の Part 登録（論理的な二重登録の防止） |
| 3 | `sha256` の重複判定 | §10.5 の `DUPLICATE_CONTENT` |
| 4 | 1 件の状態遷移 | §8.4 `record_transition()` |

`random.seed(0)` で決定的にしている。`cold` は 1 回目、`warm` は以降 4 回（書き込みは 20 回）の中央値。

> **測定環境**: Docker Desktop / Apple Silicon。**コンテナ内の overlayfs 上**で測った。
> `/data` は本番では named volume なので、**`fsync` の挙動はここと違いうる。**
> ただし後述のとおり結論は倍率の差では動かないので、この差は判断に影響しない。

### 3.2 生成結果

| ストア | 構築 | 実体サイズ |
|---|---|---|
| SQLite（`events.entity_key` **TEXT**） | 0.9 s | **70.0 MiB** |
| SQLite（`events.entity_key` **INTEGER**） | 0.7 s | **42.6 MiB** |
| ファイル方式（1 エンティティ 1 JSON） | 1.3 s | 39.9 MiB（35,040 ファイル） |

**自然キー化の代償は 3 年で +27.4 MiB である**（決定 2 の評価に使う。§6.4）。

### 3.3 1. 状態別の件数集計（§17.2 `status`）

| 方式 | cold | warm |
|---|---|---|
| SQLite `GROUP BY status` | 1.28 ms | **0.80 ms** |
| ファイル 全 JSON を読む | 321.80 ms | **315.12 ms** |
| ファイル 名前だけ（`status` をファイル名に載せた場合の下限） | 9.76 ms | 8.32 ms |

### 3.4 2. `partkey` の重複判定（§10.2）

| 方式 | warm |
|---|---|
| SQLite PRIMARY KEY で引く | **0.00 ms** |
| ファイル パスの存在確認 | **0.00 ms** |

### 3.5 3. `sha256` の重複判定（§10.5）

| 方式 | warm |
|---|---|
| SQLite 部分 UNIQUE 索引で引く | **0.00 ms** |
| ファイル `O_EXCL` マーカーの存在確認 | **0.00 ms** |

### 3.6 4. 1 件の状態遷移（§8.4 `record_transition()`）

| 方式 | cold | warm |
|---|---|---|
| SQLite 1 トランザクション（`synchronous=FULL`） | 13.76 ms | **0.78 ms** |
| ファイル `os.replace` + `fsync` ×2（ファイル + 親ディレクトリ） | 1.05 ms | **0.82 ms** |

### 3.7 実測から言えること

**性能はどちらの方式でも成立する。**

- 集計は SQLite が 390 倍速いが、**負けている側の 315 ms も CLI として十分速い。**
  `status` は人が打つコマンドであり、1 日 1 回か数回である
- 点の照会と書き込みは**ほぼ同じ**（0.00 ms / 0.78 ms 対 0.82 ms）
- 実体サイズもほぼ同じ

**したがってストアの選択は性能では決まらない。**構造で決める（§4 以降）。

> **1 点だけ注意**: 集計はファイル数に線形である。`status` が 1 種類の集計で 315 ms なら、
> `doctor` が同じ全読みを 3 種類やれば 1 秒近くなる。**SQLite なら索引を足せば済む**が、
> ファイル方式では「どの属性をファイル名に載せるか」を先に決めなければならない。
> これは性能の問題ではなく**設計の柔軟性の問題**である。

## 4. 8 軸の比較

| 軸 | SQLite が担保するもの | ファイル方式で自前になるもの | 差 |
|---|---|---|---|
| **原子性** | `record_transition()` の 1 トランザクションで `status` UPDATE と `events` INSERT を同時に行う。「`status` だけ進んで `events` が無い」状態が作れない | **1 エンティティ 1 ファイルに `events` を内包すれば `os.replace()` 1 回で同等。**実測でも 0.82 ms 対 0.78 ms | **互角** |
| **一意性（partkey）** | PRIMARY KEY | **ファイルパス自体を `partkey` にすれば `O_EXCL` で同等。**作成が成功したことが一意性の証明になる | **互角** |
| **一意性（sha256）** | 部分 UNIQUE 索引（`WHERE sha256 IS NOT NULL`）。エンティティの UPDATE と同じトランザクションに入る | **`by-sha/<sha256>` マーカーが必要。**`sha256` は §10.5 で変換しながら算出するので、エンティティが既に存在する時点で後から書く。**エンティティ本体とマーカーの 2 書き込みになり、中断すると孤児マーカーが残る**（マーカーはあるが、指す先の `sha256` が空）。§9.4 の復帰処理に「孤児マーカーの検出と修復」を足す必要がある | **SQLite 有利** |
| **ID の同一性** | **ストアと独立。**`partkey TEXT PRIMARY KEY` にすれば解決する | 同じ（パスが識別子になる） | **無関係** |
| **照会** | `GROUP BY` 0.80 ms。属性を増やしても索引を足せば済む | 全読み 315 ms。**CLI としては十分だが、集計の種類に比例して伸びる。**回避するには「どの属性をファイル名に載せるか」を先に決める（§3.7） | **SQLite 有利**（柔軟性） |
| **同時実行** | WAL + `busy_timeout`。`service` が書き、`exec` が読む。読み手はトランザクション境界で一貫したスナップショットを見る | `os.replace()` は原子的なので**1 ファイルは破れない**。ただし**複数ファイルを跨ぐ照会は一貫しない**（`status` が 35,040 ファイルを読む 315 ms の間に遷移が起きると、集計が「どの瞬間のものでもない」値になる） | **SQLite 有利** |
| **クラッシュ耐性** | WAL のロールバック | `.tmp` の残骸を §9.4 で掃く（既に `paths.safe_unlink_tmp()` がある）。**加えて孤児 sha マーカーの検出・修復が要る** | **SQLite 有利** |
| **バックアップ** | WAL のためファイルコピー不可。`Connection.backup()` を使う（`db.py` に実装済み） | **`cp -a` で足りる。**中身が JSON なので人間が読める | **ファイル方式 有利** |

**差が付くのは 4 軸で、うち 3 軸（sha256 の一意性 / 同時実行 / クラッシュ耐性）で SQLite が
有利、1 軸（バックアップ）でファイル方式が有利である。**
そして**最も重要な「ID の同一性」はストアの選択と無関係**だった。

## 5. 決定 1: SQLite を継続する

**理由は 3 つある。**

### 5.1 差が付いた 3 軸はすべて「自前で担保する」側に落ちる

ファイル方式にすると、次の 3 つを自分で書くことになる。

1. **`sha256` 索引とエンティティ本体の 2 書き込みの整合**、およびその中断からの復帰
2. **複数ファイルを跨ぐ照会の一貫性**（`status` の集計中の遷移）
3. **孤児マーカーの検出と修復**（§9.4 への追加）

**これらはすべて §14.1 の安全性が依存するモジュールに入る。**§14.1 は
「文字起こしが Vault に残っていることを確かめてから元音声を消す」条件であり、
`recordings` の行の正しさに賭けている。**その行を保持する層に自前のトランザクション処理を
足すのは、防ぎたい事故に最も近い場所でリスクを取ることになる。**

### 5.2 実測で得るものが無い

§3.7 のとおり、性能はどちらも成立する。**移行の見返りは
「`cp -a` でバックアップできる」「JSON が人間に読める」の 2 点だけ**である。

- バックアップは `db.py` の `backup()`（`Connection.backup()`）で既に解決している
- 「人間が読める」は `sqlite3 -box` で足りる。v5.0 は `history` / `show` コマンドを削除して
  **`events` テーブルを SQL で直接読む運用に切り替えた**（§17.1）ので、
  すでに「SQL で覗く」が正規の手段である

### 5.3 捨てるものが大きい

`db.py` 509 行 + `0001_initial.sql` 145 行 + テスト 704 行が既に動いている。とくに

- **`record_transition()` が状態を変える唯一の API** であることが AST 検査で固定されている
  （`db.py` の中で `status` を UPDATE する箇所が 1 か所だけであることをテストが確認する）
- マイグレーションの禁則が静的に検査されている

**この「唯一の変更経路」という性質は、ファイル方式でも再現できるが、
再現するまでの間は失われる。**移行の見返りが §5.2 の 2 点では釣り合わない。

> **「慣れているから」は理由にしていない。**上の 3 点はいずれも
> 「何がどこで担保されているか」の比較である。

## 6. 決定 2: 識別子を自然キーにする

**#60 の本当の収穫はここである。**

### 6.1 発見

> **§8.5 のドクトリン全体は「整数 ID を守るため」だけに存在している。**

§1 で見たとおり、「テーブルを作り直すな / スキーマは v1 完全形 /
`ALTER TABLE ADD COLUMN` 以外禁止」の 3 点はすべて、
**`AUTOINCREMENT` が振り直されることを防ぐため**にある。
そしてそれが必要なのは、§14.1 が `part.id in frontmatter_ids(note)` という
**整数の間接参照**で削除可否を決めているからである。

**識別子を自然キーにすると、この事故クラスが構造的に消える。**

| | v5.0 まで | v5.1 以降 |
|---|---|---|
| 識別子 | `recordings.id INTEGER AUTOINCREMENT` | `recordings.partkey TEXT`（`<device_id>/<source_folder>/<filename>`） |
| frontmatter | `voicedock_recording_ids: [41, 42, 43]` | `voicedock_recording_keys: ["DJIMIC3/TX_MIC001_.../TX01_..._orig.wav", ...]` |
| §14.1 が言っていること | 「ノートが整数 42 を含み、かつ DB が 42 を X だと言っているとき、X を消す」 | **「ノートがファイル X を含むと言っているとき、X を消す」** |
| 振り直しの危険 | ある（§8.5 の禁則で防ぐ） | **無い**（数える対象が無い） |

### 6.2 これは v5.0 の `_orig` 固定が可能にした

v4.6 までは 1 Part が最大 2 ファイル（`orig` と `denoised`）を持っていたので、
**単一のパスを識別子にできなかった。**v5.0 で `_orig` 固定にした結果（付録 A L-1）、

```text
1 Part = 1 ファイル = 1 パス = 1 識別子
```

が成り立つようになった。**簡素化が安全性の改善を可能にした例である。**

### 6.3 `partkey` の形

```text
partkey = "<device_id>/<source_folder>/<filename>"
例: DJIMIC3/TX_MIC001_20260829_071201/TX01_MIC002_20260829_071204_orig.wav
```

- **`device_id` を含める**のは `session_key`（`DJIMIC3:20260829`。§8.3）と同じ規約に揃えるため
- 旧 `partkey` 索引は `(transmitter_id, mic_index, started_at, source_folder)` だった。
  ファイル名は `transmitter_id` / `mic_index` / 時刻をすべて含むので、
  **新しい鍵は旧鍵より強い**（識別能力が落ちない）
- **削除要求（§14.1.1）が既に `device_id` + `relpath` を運んでいる。**つまり
  **削除要求の中身がそのまま `partkey` である。**reaper 検証に
  「`<device_id>/<relpath>` が `partkey` と一致すること」を足せる（検証 12）

### 6.4 代償

| 代償 | 評価 |
|---|---|
| **`events` が 3 年で +27.4 MiB**（§3.2） | **受け入れる。**`/data` の空き前提は 58 GiB（§19.2）。`entity_key` に slug（16 桁）を入れれば約 20 MiB に減るが、**それは §14.1 が消した間接参照を監査ログに再導入することになる。**監査ログは自己完結しているほうがよい（`recordings` の行が無くても何が起きたか分かる） |
| **ノートの frontmatter が 32 Part の日で約 2.4 KB 増える** | **受け入れる。**Daily ノートは約 12.8 KB（§16.2 の例）なので相対的には大きいが、**frontmatter が「何を消してよいか」の唯一の根拠である**（§14.1）。読みたくない場合は Obsidian のプロパティ非表示で隠せる |
| **ファイル名に鍵をそのまま使えない** | `device_id` は Volume 名なので空白や任意文字を含みうる（`NO NAME` / `Macintosh HD`。§5.4）。`session_key` は `:` を含む。**sanitize は衝突しうるので使わず、`key_slug(key) = sha256(key)[:16]` を使う**（§6.5） |
| **ログ行が長くなる**（`recording_id=42` → `recording_key=DJIMIC3/...`） | **受け入れる。**短い別名を作ると「ログの識別子」と「ノートの識別子」が 2 系統になり、障害時に人が突き合わせる作業が増える |

### 6.5 `key_slug` は識別子ではない

`staging` / `transcripts` / `analysis` の 3 か所はファイル名に鍵を要する。

```python
key_slug(key) = hashlib.sha256(key.encode("utf-8")).hexdigest()[:16]
```

**正は `partkey` / `session_key` であり、slug は派生値である。**
64 bit なので 36,000 件での衝突確率は約 3.5e-11 だが、**確率で安全を担保しない。**
§10.5 に歯止めを置く: `staging/<slug>/` が既に存在する場合、
`normalized_path` がそこを指す行の `partkey` が一致することを確認し、
しなければ `IMPORT_FAILED` にする。

slug から鍵への対応は、**DB が `normalized_path` / `transcript_path` / `analysis_path` を
持っているので常に SQL で引ける。**

## 7. §8.5 のドクトリンがどう変わるか

### 旧（削除する）

1. テーブルを作り直してはならない
2. スキーマは v1 完全形とする
3. v2 以降は `ALTER TABLE ADD COLUMN` に限る

### 新（1 点だけ）

> **唯一の禁則: `partkey` と `session_key` の算出規則を変えてはならない。**
>
> ノートの frontmatter には**算出した鍵そのものが載る**。算出規則を変えると、
> 既に保存したノートに載っている鍵と DB の鍵が食い違い、
> **§14.1 の「ノートがこのファイルを含むと言っているか」が偽になる。**
> **偽になる側に倒れるので削除事故にはならない**（元音声が残る）が、
> **その日以前の録音が永久に削除対象にならない。**

**テーブルの作り直しは許される。**識別子が自然キーになったので、作り直しても
`partkey` は変わらず、ノートとの対応が壊れない。ただしデータ損失のリスクは残るため、
**v2 以降は原則 `ALTER TABLE ADD COLUMN`** とし、作り直す場合は行数の一致をテストで確認する。

### テストがどう変わるか

| v5.0 まで | v5.1 以降 |
|---|---|
| `tests/unit/test_migration_rules.py` が `DROP TABLE` / `DROP COLUMN` / `ALTER TABLE ... RENAME` / `CREATE TABLE ... AS SELECT` を**構文で禁止する** | **`tests/unit/test_paths.py` が `partkey_for()` の算出結果を固定入力に対してバイト単位で固定する** |

**守るべき不変量そのものを固定するテストになる。**v5.0 までは「振り直しに繋がる構文」を
代理で禁止していた（真の不変量を直接テストできなかった）。
